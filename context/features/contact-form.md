# Contact Form
## Goals
The contact form needs to work by when the user inputs valid data, the information gets saved to a db instead of sending an email. The data in this database can be viewed via admin login. Perhaps an email can be sent to the admin as well, but the db gets updated to be viewed.
The form needs to check a valid data. The event type should be a drop down of values. On successful submissions, a success modal will be shown and the form will be cleared. 
Date selection will be from a visual calendar where the user selects the day, and I will have to include the time as well.

## Implementation

- **Scope cuts (confirmed with user before building):** Email notification skipped for now — DB-only (no email provider configured). Time selection uses a simple native `<input type="time">` next to the calendar, not a custom time-slot grid.
- **Fields expanded** to match `project-overview.md`'s recommended booking-flow set: Name, Email, Phone, Event Date, Event Time, Event Type (dropdown), Event Location, Services Interested In (multi-select checkboxes), Estimated Guest Count, Additional Details.
- **Event Type dropdown** options are pulled from the site's existing `content.eventTypes` (Weddings, Corporate, Parties, Expos & Trade Shows, Celebrations, Live Events) rather than a separate hardcoded list, keeping it consistent with the rest of the data-driven homepage.
- **Services Interested In** options are a fixed list defined in `lib/contact.ts` (`SERVICE_OPTIONS`): Event Photography, Event Video, Photo Booth Experience, 360 Photo Booth, Corporate / Brand Activation.
- **Validation:** Zod schema in `lib/contact.ts` (`contactSubmissionSchema`); the server action (`app/actions/contact.ts`, `submitContactForm`) validates with `safeParse` and returns `{ success, error }` rather than throwing.
- **Calendar:** `react-day-picker` (new dependency) in `mode="single"`, styled via its `classNames` prop with Tailwind classes to match the site's dark theme — no default stylesheet import, no shadcn scaffolding (wasn't set up in this project).
- **Form component:** `app/components/ContactForm.tsx` (client component) — uses `useActionState`. The success-modal-and-reset side effects (showing the modal, clearing the calendar selection, calling `formRef.current?.reset()`) happen directly inside the action callback passed to `useActionState`, not in a `useEffect` — doing it in an effect triggered an ESLint `react-hooks/set-state-in-effect` error, and the action-callback approach is the more correct place for it anyway (React 19 actions run in a transition).
- **Admin viewer:** new protected page `app/admin/inquiries/page.tsx` (`requireAdminSession()`, same pattern as other admin pages), linked from the dashboard's "Management" section. Lists all `ContactSubmission` rows newest-first.
- **Database — no prior migration history:** the existing tables (`User`, `SiteContent`, `MediaAsset`) had only ever been synced via `prisma db push`; `prisma/migrations/` didn't exist. Set up properly instead of continuing with `db push`:
  - `prisma/migrations/20260916120000_baseline/migration.sql` — represents the 3 pre-existing tables (generated connection-free via `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script`).
  - `prisma/migrations/20260917120000_add_contact_submission/migration.sql` — just the new `contact_submissions` table (generated connection-free by diffing a saved copy of the old schema against the new one with `--from-schema`/`--to-schema`; diffing via `--from-migrations` needs a shadow database connection, which is blocked on this network — the schema-file-to-schema-file diff mode doesn't need one).
  - `start` script updated to `prisma migrate deploy --config prisma7.config.ts && next start` so Render applies future migrations automatically on deploy.
  - **Outstanding one-time manual step (not done by Claude — needs a network where Neon's port isn't blocked, e.g. Render's shell):** run `prisma migrate resolve --applied 20260916120000_baseline --config prisma7.config.ts` **and** `prisma migrate resolve --applied 20260917120000_add_contact_submission --config prisma7.config.ts`. Both need resolving (not just the baseline) because the `contact_submissions` table was applied directly against the live Neon DB via the Neon HTTP client (`@neondatabase/serverless`, same approach used to fix login) for local testing, bypassing the blocked-TCP migration CLI — so by the time this step runs, the DB already reflects both migrations. Skipping this step means Render's first `migrate deploy` will fail trying to `CREATE TABLE` for tables that already exist.
  - Verified end-to-end against the live Neon DB: created and then deleted a real `ContactSubmission` row via the Prisma HTTP adapter to confirm the model/adapter combination works (arrays, optional int, DateTime all round-tripped correctly).
