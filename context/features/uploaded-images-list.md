# Uploaded Images List
## Goals
Images are able to be uploaded to cloudinary via admin pages, but the admin needs a way to see all of the images that are uploaded to cloudinary. Specifically all of the links so that they can decide which image URL to use or switch. They must have access to all that is available of which they uploaded. A list of uploaded images is what we need.

## Implementation

- Confirmed with user: query Cloudinary's Admin API live rather than wiring up the existing unused `MediaAsset` Prisma model — most of this site's real photos were added directly in Cloudinary's dashboard rather than through this app's uploader, so a DB-tracked list would miss them and fail to show "all that is available." No database changes.
- New `lib/cloudinary.ts`: configures the Cloudinary SDK from the existing `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` env vars (already used for signed uploads) and exports `listUploadedImages()`, which calls the Admin API's `resources` endpoint for `resource_type: "image"`, paginating via `next_cursor` until exhausted, sorted newest first.
- New `app/admin/images/UploadedImagesList.tsx` (client component): renders a thumbnail grid with each image's `public_id` and a "Copy Link" button (`navigator.clipboard`), with brief "Copied!" feedback.
- `app/admin/images/page.tsx` now also calls `listUploadedImages()` and renders the list below the existing uploader — kept on the same page/route rather than a separate one, since `/admin/images` is already the single "Image Manager" link from the dashboard.
- Verified the Admin API integration directly against the live Cloudinary account (outside the app, via a throwaway script): confirmed real images and URLs come back correctly, and that the account has more images than a single page (`next_cursor` present), exercising the pagination loop.
- Follow-up: user reported "extra" images showing up. Investigated directly against the live account — it has a `clear-choice` folder (41 real site images) alongside unrelated `samples`/`square-deli-menu`/root-level content (these were the "extras"). This account uses Cloudinary's Dynamic Folder mode, where folder is a separate `asset_folder` field, not a `public_id` prefix — a plain `prefix` filter on `resources()` returns nothing; the correct call is `resources_by_asset_folder("clear-choice", ...)`, which was verified directly to return exactly the 41 real images and nothing else.
- Also updated the signed-upload flow (`app/api/cloudinary-sign/route.ts`, `app/admin/images/UploadClient.tsx`) to upload new images into the `clear-choice` folder too (confirmed with user) — otherwise new uploads through this app's own uploader would land outside the filtered folder and never show up in the list. Verified end-to-end with a real signed test upload (asset landed in `asset_folder: "clear-choice"` as expected, then deleted as cleanup).
- Follow-up: added the ability to remove an image. New `deleteUploadedImage(publicId)` in `lib/cloudinary.ts` (calls `uploader.destroy` with `invalidate: true` to also bust the CDN cache), wrapped by a new admin-session-guarded Server Action `removeUploadedImage` (`app/actions/images.ts`). `UploadedImagesList.tsx` gained a "Delete" button per image, gated behind a `confirm()` prompt (a plain confirm rather than the password-modal pattern used for admin-user removal, since this is a lower-stakes destructive action). Verified the full upload → delete → re-list cycle directly against the live account.
